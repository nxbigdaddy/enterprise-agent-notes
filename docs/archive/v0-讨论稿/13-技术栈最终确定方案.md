## 1. Tier 0 · 最小可用（就是它，先做这个）

| 层 | 方案 |
|---|---|
| 后端 | **Python 3.12 + FastAPI** + SQLAlchemy 2.0 + Alembic + Pydantic v2 |
| 异步任务 | **APScheduler**（跑在 app 进程内）+ 一张 PG 任务表 |
| 数据库 | **PostgreSQL 16 + pgvector** |
| 文件存储 | **本地磁盘卷** + `storage.py` 抽象层（预留 S3 接口） |
| 前端 | **React 18 + TypeScript + Vite + Ant Design 5** |
| AI 调用 | **httpx 直连 + `gateway.py`**（路由 / 日志 / 配额 / fallback 一个文件） |
| 检索 | **pgvector HNSW + 权限前置过滤**；关键词用 `pg_trgm` 兜底 |
| 文档处理 | **python-docx / openpyxl / python-pptx / PyMuPDF** |
| 认证 | 企微扫码 → JWT（Authlib + PyJWT） |
| 日志 | **structlog → stdout**（看 `docker logs`） |
| 部署 | **Docker Compose：nginx + app + postgres** |

**没有的东西**：Redis、Celery、MinIO、消息队列、向量数据库、K8s、Prometheus、Grafana、Loki、OTel、Langfuse、Temporal、LiteLLM、Elasticsearch、Monorepo。

### 1.1 仅有的一处"抽象"必须保留

`ai/gateway.py` —— 业务代码里**不允许出现任何厂商 SDK 或 API key**：

```python
async def chat(messages, *, scene: str, data_level: str, user) -> ChatResponse:
    # 1. 查路由表（按 scene + data_level 选模型）
    # 2. 查配额（用户 / 部门）
    # 3. httpx 调用，失败走 fallback 链
    # 4. 写 ai_call_log（模型 / token / 费用 / 耗时 / trace_id）
    # 5. 记录密级路由决策（供审计）
```

约 200 行，但它同时解决了统一出口、配额、成本、审计、降级五件事。
**判断标准**：换掉这个文件需要改业务代码，就说明抽象失败了。

### 1.2 检索就这么写（不要提前优化）

```sql
-- 建表
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;      -- 中文关键词兜底（tsvector 对中文无效）

CREATE TABLE kb_chunk (
  id bigserial PRIMARY KEY,
  doc_id bigint NOT NULL,
  content text NOT NULL,
  embedding vector(1024),            -- 先用普通 vector，别用 halfvec
  dept_id bigint,                    -- 权限字段，建索引
  data_level smallint
);
CREATE INDEX ON kb_chunk USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON kb_chunk (dept_id, data_level);        -- 前置过滤
CREATE INDEX ON kb_chunk USING gin (content gin_trgm_ops);  -- 关键词兜底
```

> ⚠️ **不要用 `to_tsvector('simple', content)`**：PG 默认解析器会把整段无空格的中文当成一个 token，索引等于没用。中文兜底用 `pg_trgm`；若真需要分词检索再装 `zhparser` / `pg_bigm`。

检索顺序：**先按权限过滤 → 再向量检索**。这就是 Tier 0 的全部检索逻辑。

> 不做混合检索 RRF、不做重排、不做 halfvec、不做迭代扫描调优——这些是**准确率不达标时才加的补丁**，不是起点。

### 1.3 依赖 MaxKB 后的变化（待确认）

公司已有 **MaxKB 专业版**（能力齐备但基本未使用）。若按 [15-MaxKB复用分析.md](./15-MaxKB复用分析.md) §9 的「策略 B+」执行——**知识检索交给 MaxKB，我们的 Agent 做统一入口**——则 Tier 0 相应变化：

| 变化 | 说明 |
|---|---|
| ➖ **pgvector 可以不用** | 检索在 MaxKB 内完成，我们的 PG 只做关系数据 |
| ➖ 知识库管理后台不用自建 | 用 MaxKB 的 |
| ➖ 文档解析 / 向量化流水线不用自建 | 用 MaxKB 的 |
| ➕ MaxKB 集成（API 调用 + 引用展示 + 审计记录） | 约 1 人周 |
| ⚠️ **MaxKB 的模型端点必须指向我们的 AI 网关** | 否则绕过统一出口，成本与审计失效 |
| ⚠️ **知识库按「部门库 + 公共库 + 专项库」组织** | 用 MaxKB 原生用户组授权，避开文档级打标签方案 |

**MVP 工期：约 21 人周 → 约 17.5 人周（3 人约 6 周）。**

> 状态：**待确认**。前置条件是查清 MaxKB 闲置的根因（见文档 15 §9.2）——若根因是「没有内容」或「没有负责人」，集成一个空知识库没有意义。

## 2. Tier 0 砍掉了什么，代价是什么

诚实列清楚，避免以后觉得"漏了"：

| 砍掉 | 代价 | 什么时候加回来 |
|---|---|---|
| **Redis** | 不能多节点；无分布式限流与缓存 | 应用节点 > 1 |
| **Celery** | 任务与 Web 同进程；重启丢内存态（PG 任务表可恢复） | 任务量 > 数百/天 |
| **MinIO** | 文件在本地卷，无副本，备份靠自己 | 需多节点，或文件 > 100GB |
| **Docling** | 复杂表格 / 扫描件解析质量差 | 要处理扫描件或复杂版面 |
| **Rerank** | Top-5 命中率低一些 | **问答准确率不达标时第一个加** |
| **混合检索 RRF** | 精确编号（工号/合同号）匹配弱 | 用 `tsvector` 兜底够撑一阵 |
| **halfvec / 迭代扫描** | 内存占用高、带过滤时召回略降 | chunk > 100 万 |
| **Prometheus/Grafana** | 没有可视化大盘 | 有人专职做运维时 |
| **ECharts** | 没有图表 | 需要报表时 |
| **TanStack Query / Zustand** | 状态管理代码多一些 | 前端页面 > 15 个 |
| **Monorepo** | 三端无法共享类型 | 第二个客户端启动时 |
| **Electron / 企微 H5** | 只有 Web 端 | MVP 验证通过后 |

**没有一项是"以后补要返工"的**——因为都留了接口或与之无关。唯一必须现在做对的是 §1.1 和 §1.2 那两处。

## 3. 什么时候升级（按规模，不按时间）

| 规模 | 层级 | 加什么 |
|---|---|---|
| **< 500 用户，单节点** | **Tier 0** | 就是上面这些 |
| 500 ~ 2000 用户 | Tier 1 | Redis、Celery、MinIO、Docling、Rerank、Prometheus+Grafana、Electron、企微 H5、Monorepo、管理后台 |
| > 2000 用户 / 多节点 | Tier 2 | LiteLLM、Temporal、Qdrant、K8s、Langfuse、gVisor、配置中心 |

**每个组件的触发条件**（满足才加，不要提前）：

| 组件 | 触发条件 |
|---|---|
| Redis | 应用节点 > 1 |
| Celery | 任务量 > 数百/天，或任务需要独立扩缩容 |
| MinIO | 需要多节点共享文件，或文件量 > 100GB |
| Rerank | 知识问答准确率 < 80% |
| Docling | 出现扫描件 / 复杂表格需求 |
| halfvec | chunk > 100 万（内存吃紧） |
| Qdrant | chunk > 500 万，或检索 p99 < 50ms |
| LiteLLM | 模型数 > 3，或需要按部门发虚拟密钥 |
| Temporal | 出现「等待人工确认数小时以上」的流程 |
| K8s | 应用节点 > 6 |
| Langfuse | 需要 prompt A/B 与自动化评测 |

## 6. v1.0 → v1.1 变更记录

被反馈「过于复杂」，砍掉以下 12 项：

| 砍掉 | 原方案 | 改为 |
|---|---|---|
| Celery + Redis | 独立 broker 与 worker | APScheduler + PG 任务表 |
| Redis（缓存/限流） | 独立实例 | 进程内 + JWT 无状态 |
| MinIO | 独立对象存储 | 本地磁盘卷 + storage 抽象 |
| Docling | 复杂版面解析 | python-docx / PyMuPDF |
| Rerank 模型 | bge-reranker + TEI | 先不做 |
| 混合检索 RRF | tsvector + 向量融合 | 向量为主，tsvector 兜底 |
| halfvec + 迭代扫描 | 内存优化 | 普通 vector |
| Prometheus + Grafana + Loki + OTel | 完整可观测 | structlog → stdout |
| TanStack Query + Zustand | 前端状态库 | React 内置状态 |
| Monorepo + Turborepo | 三端共享 | 单前端工程 |
| ECharts | 图表 | 先不做 |
| 自研权限三张表 | 独立模块 | 沿用（这条没砍，成本本来就低） |

**部署单元从 6 个降到 3 个。**

## 7. 明确不做的事
