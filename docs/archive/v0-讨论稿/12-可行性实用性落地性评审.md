## 0. 结论摘要

| # | 结论 | 严重度 |
|---|---|---|
| **C1** | 当前文档集的功能量约为 **71 人周**，3 人团队需 **8~10 个月**才能全部落地。而 P0 清单有 25 项——**意味着 8 个月内没有任何东西可上线**，这是项目最大的失败风险 | 🔴 致命 |

## 1. 评审口径

| 维度 | 定义 | 判据 |
|---|---|---|
| **可行性** | 技术上能不能做出来 | 有无成熟方案？有无硬依赖？ |
| **实用性** | 值不值得做 | 真实使用频次 × 节省时间 ÷ 建设成本 |
| **落地性** | 能不能按期按质交付 | 依赖多少外部条件？团队能力是否匹配？ |

## 4. 过度设计清单（必须砍）

这些在技术上都是正确选择，但**对当下阶段是负债**：

| 原方案 | 问题 | 改为 | 何时再引入 |
|---|---|---|---|
| **Temporal**（工作流） | 引入 Go 服务 + 确定性编程约束；MVP 无真实复杂流程 | **Celery + Redis + 数据库状态机** | 出现「等待人工确认数小时/数天」且状态机失控时 |
| **Langfuse**（LLM 可观测） | 与自建审计中心 + `ai_call_log` 表功能重复 | **`ai_call_log` 表 + Grafana** | 需要 prompt A/B 对比与自动评测流水线时 |
| **Casbin**（权限引擎） | policy 语法学习成本 > 收益；需求只是角色+能力+数据范围 | **自研三张表**（角色/能力/数据范围规则） | 策略复杂到需要表达资源级条件时 |
| **K8s / Nomad**（编排） | 千人规模不需要 | **Docker Compose** | 应用节点 > 6 或需弹性伸缩时 |
| **gVisor**（沙箱） | 早期无不可信代码 | **Docker 限权容器**（禁网/只读根/资源上限） | 需执行用户提交的任意代码时 |
| **Milvus / Qdrant**（向量库） | 起量前无必要 | **pgvector + halfvec + HNSW** | chunk > 500 万（见 §8） |
| **RabbitMQ** | Celery 用 Redis 做 broker 足够 | **Redis 作 broker + backend** | 需要复杂路由/持久化保证时 |
| **四协议邮件接入** | 同时支持 Graph/EWS/IMAP/Gmail 是 4 倍工作量 | **只接公司实际那一个** | 真有第二个系统时 |
| **Python sidecar（默认）** | 增加分发复杂度、体积、杀软误报 | **按需引入**：只有出现 COM/UIA/硬件 DLL 才挂 | 见 `11` 文档的能力清单 |
| **MCP 本地插件体系** | MVP 只需本机文件读写，不需要插件宿主 | **直接实现文件能力** | 出现第二个本地系统集成需求时 |
| **Nacos/Consul/etcd** | 配置量不需要配置中心 | **环境变量 + 数据库配置表 + 热更新** | 多环境多节点配置漂移时 |
| **APISIX/Kong** | 不需要独立网关 | **Nginx + FastAPI 中间件** | 需要跨语言统一网关时 |

### 4.1 保留但降配的

| 组件 | 原方案 | 降配为 | 理由 |
|---|---|---|---|
| AI 网关 | LiteLLM Proxy | **MVP：自研薄网关（约 200 行）；P1 若模型 > 3 个再切 LiteLLM** | 单模型时引入 LiteLLM 是为将来付费 |
| 可观测 | OTel + Prometheus + Grafana + Loki + Langfuse | **MVP：结构化日志 + Prometheus + Grafana；P1 加 Loki/OTel** | |
| 管理后台 | 独立前端工程 | **MVP：DB 脚本 + 极简页面；P1 做完整后台** | 5 人周占比过高 |
| Agent 工具 | 声明式注册表 + 动态加载 | **MVP：硬编码 5 个工具** | 工具数量少时注册表是负担 |

> **可替换性设计**：薄网关实现为内部 `AIGateway` 接口，后面换成 LiteLLM 只改一个实现类。这样"降配"不等于"技术债"。

## 6. 实用性：功能价值排序

按「建设成本」与「采用率」交叉：

```
高采用率 ┤  知识问答 ★        邮件摘要 ★
         │  文档生成 ★        待办/通知 ★
         │  ─────────────────────────────
         │  日程会议           桌面端本机文件
低采用率 ┤  多Agent            工作流引擎
         │  技能市场           RPA / 连接器
         └──────────────────────────────────
            低成本              高成本
```

**反直觉的发现**：
- **成本最低的三个（知识问答、邮件摘要、文档生成）采用率最高**；
- **成本最高的三个（工作流引擎、桌面端、连接器）采用率最低**；
- 而原文档的路线图把桌面端和工作流放在了 P1 的核心位置。

**建议**：把资源集中在左上象限。桌面端不是不要，是**不该在验证价值之前做**——它是最贵的一块，且依赖最多的外部条件（安全评审、本地系统清单、代码签名、双运行时）。

## 8. 容量与成本可行性（技术数据）

这是原文档最缺的部分——可行性必须有数字。

### 8.1 假设

| 指标 | 假设值 |
|---|---|
| 员工总数 | 2,000 |
| 日活 | 400~600 |
| 峰值并发 | 50~100 |
| 知识库文档量 | 20 万份 |
| 切分后 chunk 数 | 100~200 万 |
| 人均日 token 消耗 | 5~15 万 |

### 8.2 向量存储的真实占用（关键数据）

根据 pgvector 生产实践（[ClickHouse Engineering: Scaling vector search in Postgres](https://clickhouse.com/resources/engineering/scale-vector-search-postgres)）：

- 1536 维 fp32 向量**裸存储约 6KB/条**，但计入 HNSW 图结构的指针与邻居列表后，**实际约 20~25KB/条**；
- 100 万向量 → 数十 GB 内存；1,000 万向量 → 内存成为核心设计约束；1 亿向量 → 仅 fp32 裸存储就超 600GB。

**换算到本项目**（BGE-M3，1024 维，用 `halfvec` FP16）：

| chunk 数 | 裸存储 | 含 HNSW 开销 | 建议 PG 内存 |
|---|---|---|---|
| 50 万 | ~1GB | ~5GB | 16GB |
| **100 万** | ~2GB | **~10GB** | **32GB** |
| 200 万 | ~4GB | ~20GB | 32~64GB |
| 500 万 | ~10GB | ~50GB | 需评估迁移 |

**结论**：**32GB 内存的 PG 节点可支撑约 200~300 万 chunk**，覆盖本项目 3~5 年内的知识库规模。超过 500 万 chunk 再评估 Qdrant。

### 8.3 两个硬约束（必须写进设计）

1. **维度上限**：pgvector 的 `vector` 类型对 HNSW/IVFFlat 索引有 **2,000 维硬上限**。若选 3,072 维的模型（如 `text-embedding-3-large`），`CREATE INDEX USING hnsw` 会因单条索引项超出 Postgres 8KB 页限制而**失败**。解决办法是用 `halfvec`（上限 4,000 维）或降维。**BGE-M3 是 1024 维，安全**——这也是选它的一个实际理由。

2. **先过滤后召回有官方实现**：pgvector **0.8+ 提供迭代索引扫描**，专门解决"带元数据过滤时召回率崩塌"的问题（后过滤会导致请求 10 条、过滤掉 9 条、只剩 1 条）：
   ```sql
   SET hnsw.iterative_scan = strict_order;   -- 或 relaxed_order
   ```
   配合 `hnsw.max_scan_tuples` 限制扫描上限防止查询跑飞。**这直接落实了 `04` 文档"先过滤后召回"的要求，且不需要上专用向量库。**

3. **混合检索也不需要外部引擎**：Postgres 原生可用 `tsvector` + GIN 做词法检索，与向量结果用 **RRF**（`sum(1/(60+rank))`）融合。BM25 可用 `vchord_bm25` / ParadeDB 扩展补齐。

### 8.4 硬件预算（估算）

| 角色 | 配置 | 数量 | 说明 |
|---|---|---|---|
| 应用节点 | 8C 16G | 2 | FastAPI × 4 worker + Celery worker |
| 数据节点 | 8C 32G | 2 | PG 16 + pgvector，主备 |
| 对象存储 | 4C 8G + 2TB | 1 | MinIO |
| Redis | 2C 4G | 1 | 可与应用同机 |
| GPU（可选） | 单卡 24GB × 2 | 1 台 | 7B~14B 模型；无则全走外部 API |

**无 GPU 的起步方案总成本约 5~6 台虚拟机**，完全可行。

## 10. 评审结论：三条必须接受的现实

1. **能力清单不能当路线图用。** 71 人周的全量清单必须先压缩到 23 人周的 MVP，否则 8 个月内没有任何东西能上线。
2. **技术不是瓶颈，范围和外部依赖才是。** E1~E8 八个前置条件中有 5 个不受研发团队控制，必须最先启动。
3. **最贵的功能恰好最不实用。** 桌面端、工作流、连接器占全量工期的 30%+，但对采用率的贡献最低——它们应该是价值验证**之后**的投资，而不是之前。
