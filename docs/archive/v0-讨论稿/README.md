# 企业内部办公 Agent —— 设计文档

> 版本：v0.1（草稿） · 状态：需求成型中 · 本文档集为**讨论稿**，非最终方案

## 一、一页速览

| 项目 | 内容 |
|---|---|
| **一句话定位** | 公司内部统一的 AI 办公入口：一个账号、一个助手、三端可用，把散落在邮件/文档/系统里的工作收敛到一处完成 |
| **交付形态** | Web 端 + 桌面端（Windows / macOS）+ 移动端（企业微信内置浏览器 H5） |
| **核心差异点** | 不是「一个聊天窗口」，而是**能碰公司数据和本机文件的执行体**——因此治理能力（权限、审计、成本、安全）与业务能力同等重要 |
| **建设方式** | 平台化建设：底座（AI 网关 / 用户权限 / 审计 / 可观测）+ 场景能力（邮件、文档、知识库、工作流）分层演进 |
| **最大风险** | 不是模型效果，而是 ①数据泄露面（桌面端 + 邮件）②权限穿透（RAG 检索越权）③成本失控 |
| **成功标准（示例）** | 试点部门周活跃 ≥ 60%；每人每周节省 ≥ 3 小时；越权/外发事故 0 起；单次任务综合成本可核算 |

## 二、已明确的需求（来自需求方）

1. **统一的 AI API 管理**：既能接外部模型 API，也能接内部自建模型，统一出口、统一治理。
2. **统一的用户管理**：一套账号体系，贯穿三端。
3. **基础功能 + 分级功能**：所有员工有基础能力，不同角色/部门按需开通不同功能。
4. **三端互通**：桌面端与 Web 端互通；移动端以企业微信自建应用为入口，通过企微内置浏览器访问；**三端数据互通**。
5. **桌面端本地能力**：本机文件管理；连接本机上的各类系统/客户端/本地服务。
6. **邮件管理**：读、分类、摘要、拟稿、发送与跟进。
7. **技术栈约束（硬性）**：不使用任何 Java / JVM 相关技术。详见 [10-技术栈选型.md](./10-技术栈选型.md)。

## 四、贯穿全局的六条设计原则

1. **服务端是唯一事实源**：三端只是视图与本机能力代理，会话、上下文、文件元数据、权限一律以服务端为准，避免三端状态漂移。
2. **默认最小权限 + 显式授权**：能力（工具）和数据都要显式开通；默认拒绝，而不是默认放开后再收窄。
3. **凡是有外部副作用的动作，必须可确认、可追溯、可撤销**：发邮件、改文件、删数据、对外提交。
4. **AI 网关是治理层，不是转发层**：没有配额、审计、脱敏、降级的网关等于没有网关。
5. **能力可插拔**：模型、知识库、连接器、工具都以插件/注册表方式接入，避免被单一厂商或单一系统绑死。
6. **先跑通闭环，再谈智能**：一个「能稳定完成周报」的窄场景，价值高于十个演示级 Demo。

## 五、待决策清单（需要需求方拍板）

| # | 决策项 | 影响 |
|---|---|---|
| D1 | 数据是否允许出内网？ | 决定外部 API 与自建模型的比例，是架构第一约束 |
| D2 | 部署形态：全私有化 / 混合 / 公有云？ | 决定基础设施成本与交付周期 |
| D3 | 模型策略：外部 API 为主，还是自建推理为主？ | 决定成本模型与运维投入 |
| D4 | 首批试点部门与 3 个标杆场景 | 决定 P1 的功能排序 |
| D5 | 桌面端技术栈：Electron 还是 Tauri？ | 决定包体、性能、原生能力接入难度 |
| D6 | 邮件系统类型：Exchange / 腾讯企业邮 / 自建 / 混合？ | 决定接入协议与实现成本 |
| D7 | 权限粒度：角色级 / 文档级 / 字段级？ | 决定 RAG 与数据层的改造成本 |
| D8 | 是否允许 Agent 自主对外发信或操作本地文件？确认点设在哪？ | 决定安全模型与人机协同方式 |
| D9 | 是否需要按部门成本分摊与结算？ | 决定配额系统复杂度 |
| D10 | 是否已有企业微信自建应用的创建与审批权限？ | 决定移动端工期（常被低估） |

## 六、文档维护约定

- 每份文档顶部维护 `版本` 与 `状态`；重大结论变更时新增小节而非直接覆盖，保留决策痕迹。
- 需求方评审后的结论，回写到本文档「待决策清单」并标记为 `已定`。
- 术语统一：**能力**=对用户可见的功能；**工具（Tool）**=Agent 可调用的原子操作；**连接器（Connector）**=对外部系统的集成；**技能（Skill）**=一组工具 + 提示词 + 流程的封装。
