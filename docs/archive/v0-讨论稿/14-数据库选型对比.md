# 14 · 数据库选型：为什么是 PostgreSQL 而不是 MySQL

> 版本：v0.1 · 类型：决策记录（ADR）
> 结论：**维持 PostgreSQL**，理由见 §1。

---

## 1. 对这个项目而言，决定性理由只有一条

**pgvector —— 向量检索。**

「知识问答」是 MVP 三个场景里最重要的一个，它的实现依赖语义检索。而 MySQL 没有生产可用的 ANN 向量索引：

| | PostgreSQL + pgvector | MySQL |
|---|---|---|
| 向量类型 | `vector` / `halfvec` / `sparsevec` | 9.x 起有 `VECTOR` 类型，但**社区版的向量索引支持仍在演进**（native vector index 目前还是 feature request） |
| ANN 索引 | **HNSW / IVFFlat**，毫秒级 | 社区版**没有**；只能全表扫描算距离 |
| 100 万条 1024 维查询 | 毫秒级 | **秒级**（O(n) 暴力搜索） |
| 生产可用形态 | 装个扩展即可 | 需要 Oracle HeatWave（云专有）或阿里 AliSQL / PolarDB（云厂商分支） |

关于暴力搜索的代价有具体数据可参考：100 万条 1024 维向量、单次查询需 10 亿次乘法运算，实测延迟在**秒级**；ANN 索引把它降到毫秒级，速度差**100~200 倍**，代价是 95~99% 的召回率（[dbaplus：MySQL 硬扛 RAG 的坑](https://dbaplus.cn/news-160-7346-1.html)）。

> **关键推论**：如果坚持用 MySQL，就必须**再引入一个专门的向量数据库**（Milvus / Qdrant）。那样从「1 个数据库」变成「2 个数据库 + 1 条数据同步链路」——比自己写 SQL 复杂得多。上一版方案被说"太复杂"，而选 MySQL 恰恰会把复杂度加回来。

## 2. 其他差别（都不是决定性的，但值得知道）

| 维度 | PostgreSQL | MySQL |
|---|---|---|
| 向量检索 | ✅ pgvector（HNSW/IVFFlat） | ❌ 社区版无 |
| JSON 支持 | `JSONB` + GIN 索引，可索引可查询 | `JSON` + 函数索引，能力弱一档 |
| 索引类型 | GIN / GiST / BRIN / 部分索引 / 表达式索引 | B+Tree / 全文 / 空间 |
| 扩展生态 | 极强（pgvector、pg_trgm、PostGIS、pg_cron、pg_partman…） | 弱 |
| DDL 事务性 | DDL 可回滚 | DDL 隐式提交，不可回滚 |
| 约束能力 | CHECK / EXCLUDE / 部分唯一索引 / DEFERRABLE 外键 | 8.0.16 起才真正支持 CHECK |
| 复杂查询 | 窗口函数 / CTE / 并行查询更强 | 8.0 之后够用 |
| 高并发简单查询 | 好 | 传统上略强（差距在缩小） |
| **中文全文检索** | ⚠️ **需额外装 zhparser / pg_bigm**；或用 `pg_trgm` 兜底 | ✅ **内置 ngram 分词器，开箱可用** |
| 运维人才 | 少一些 | ✅ **国内 MySQL DBA 明显更多** |
| 云服务成熟度 | 有 | ✅ RDS MySQL / PolarDB 更普及 |
| 国产化替代 | openGauss / GaussDB / KingbaseES / Vastbase | TiDB / OceanBase / GoldenDB |
| 许可 | PostgreSQL License（宽松） | GPLv2（Oracle 持有） |

### MySQL 的两个真实优势（不否认）

1. **中文全文检索开箱可用**（内置 ngram 分词器），PG 要装扩展。
2. **国内 DBA 和运维资料更多**，出问题好找人。

但在本项目中：

- 全文检索在我们的设计里**只是"精确编号兜底"**（工号、合同号、产品代号），用 `pg_trgm` 甚至 `LIKE` 就够，不需要真正的分词检索；
- PG 的 Docker 镜像、备份、主从复制同样成熟，且我们只用单节点起步，运维面很窄。

---

## 3. 什么情况下我会改推 MySQL

诚实地说，下面这些情况 MySQL 更合适：

1. 公司已有成熟的 MySQL 团队和运维体系，且**知识库可以不做语义检索**（只做关键词）；
2. 已经有 MySQL，且已经另外有向量库；
3. 团队完全没有 PG 经验，而工期极紧。

**这三条在本项目都不成立**：知识问答是核心场景，而我们明确不想引入第二个数据库。

---

## 4. 结论

> **选 PostgreSQL 不是因为「PG 更好」，而是因为它能让一个数据库同时承担关系数据 + 向量检索 + 关键词兜底三件事。**
>
> 换成 MySQL，这三件事会变成「MySQL + 向量库 + ES」三套系统——那是复杂度翻倍，不是节省。

**保持 [13-技术栈最终确定方案.md](./13-技术栈最终确定方案.md) 中的 PostgreSQL 16 + pgvector 不变。**

## 5. 附带修正：中文全文检索的实现方式

审查本题时发现 `13` 文档 §1.2 有一处错误：`to_tsvector('simple', content)` 对**中文无效**——PG 默认解析器会把整段无空格的中文当成一个 token，索引等于没用。

**正确做法**（按推荐顺序）：

| 方案 | 说明 |
|---|---|
| **`pg_trgm`**（推荐兜底） | `CREATE INDEX ... USING gin (content gin_trgm_ops)`，支持中文子串与模糊匹配，无需额外编译 |
| `pg_bigm` | 二元分词，对中文/日文效果好，需装扩展 |
| `zhparser` | 真正的中文分词，效果最好，但需要编译 SCWS，安装成本略高 |
| `LIKE '%关键词%'` | 表小时够用，最简单 |

Tier 0 建议直接用 `pg_trgm`。
