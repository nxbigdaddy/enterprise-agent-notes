# 15 · 是否复用 MaxKB 的架构决策

> 版本：v1.0 · 类型：ADR（架构决策记录）
> 本文**不考虑 MaxKB 目前的推广与使用状况**，只回答一个问题：
> **我们新建的这套系统，有必要利用 MaxKB 吗？**
>
> 事实来源：[MaxKB 产品版本对比](https://maxkb.cn/price)

---

## 0. 结论

> **值得用，但只当作「检索组件」，不当作「并列平台」。**

| | 判断 |
|---|---|
| 有没有必要利用？ | **有**。它解决的是我们最难自己做好的那一块（文档解析 + 切分 + 向量化 + 检索调优），省 6~9 人周 |
| 能不能当主平台？ | **不能**。它是应用层产品，有自己完整的 UI / 用户体系 / 应用与智能体概念，与我们要做的主平台**功能重叠且会互相打架** |
| 正确姿势 | **降级为一个被调用的检索服务**，封装在 `Retriever` 接口后面 |

**一句话**：把 MaxKB 当**库**用，不要当**平台**用。

---

## 1. 它能提供什么（客观能力）

MaxKB V2，社区版不限制用户/应用/知识库数量；**专业版**（￥4.8万/套永久授权，次年起 ￥9600/年维保）额外提供：

| 能力 | 社区版 | 专业版 |
|---|---|---|
| 知识库管理（通用 / Web 站点 / 工作流知识库） | ✅ | ✅ |
| 文件类型（MD / DOCX / PDF / TXT / HTML / XLSX / CSV 等） | ✅ | ✅ |
| 向量检索 + 重排（支持向量模型、重排模型） | ✅ | ✅ |
| 智能体 + 可视化工作流编排 | ✅ | ✅ |
| 工具 / MCP / Skills / 触发器 | ✅ | ✅ |
| 模型管理（LLM / 向量 / 重排 / 多模态 / ASR / TTS） | ✅ | ✅ |
| **开放 API** | ❌ | ✅ |
| **完整 RBAC + 对话用户授权** | ❌ | ✅ |
| **企微 / 钉钉 / 飞书应用接入 + 扫码登录** | ❌ | ✅ |
| 系统操作日志 | ❌ | ✅ |
| SSO（LDAP / OIDC / CAS / OAuth2 / SAML2） | ❌ | ✅ |
| 多租户 / 集群部署 | ❌ | ❌（企业版才有） |

技术栈：**Python（Django）+ Vue**，符合「不使用任何 Java / JVM 技术」的硬约束。

---

## 2. 它能替代我们方案的哪一层

| 我们方案的模块 | MaxKB | 说明 |
|---|---|---|
| 文档解析 / 切分 / 向量化 | ✅ **完全覆盖** | 含 8+ 文件类型、自定义文件类型 |
| 向量检索 + 重排 | ✅ **完全覆盖** | |
| 引用溯源 | ✅ 基本覆盖 | 可返回引用片段 |
| 知识库管理后台 | ✅ **完全覆盖** | 省掉自建 |
| 问答编排 / 工作流 | ⚠️ 覆盖但**不建议用** | 见 §4 |
| 企微应用接入 / SSO | ⚠️ 覆盖但**不建议用** | 会造成双份用户体系 |
| **AI 能力网关**（配额 / 成本 / 密级路由） | ❌ 不覆盖 | 它是应用层，没有这些治理能力 |
| **邮件管理** | ❌ 不在范围 | |
| **文档生成（Word/Excel/PPT 产出）** | ❌ 不在范围 | 它有"内容生成"，不是 Office 文件产出 |
| **桌面端本机文件 / 本地系统** | ❌ 不在范围 | |
| **组织架构同步 / 待办 / 通知中心** | ❌ 不在范围 | |
| **三端统一体验** | ❌ 无法融入 | 它有自己的界面 |

**结论**：它只覆盖「知识问答」这一个场景的检索侧，以及知识库管理后台。**其余 70% 的工作量它都不管。**

但**恰恰是这一块最值得复用**——因为文档解析、切分策略、embedding 选型、召回率调优，自研第一版大概率不如一个成熟的商业产品。这是它最实在的价值。

---

## 3. 引入它的真实代价（这才是决策重点）

技术上都好说，真正的成本在架构与组织：

| # | 代价 | 严重度 |
|---|---|---|
| C1 | **多一个系统**：我们辛苦把方案简化到 3 个容器，引入它就变成 4~5 个容器 + 一套独立数据库 + 一条独立升级路径，方向相反 | 🟠 |
| C2 | **它是应用层，不是组件**：有自己的 UI、用户体系、"应用/智能体"概念。用应用层产品当组件，长期一定会别扭 | 🟠 |
| C3 | **功能重叠 = 两个平台赛跑**：它自己就在做智能体、工作流、工具、MCP、企微接入、触发器——**这些正是我们要做的**。半年后必然出现"MaxKB 也能做，你们为什么重做"的质疑；或者我们做完的功能它升级就有了，白做 | 🔴 |
| C4 | **双份用户与权限体系**：我们有企微组织 + SSO，它也有。要做部门级授权就得维护两套组织同步 | 🟠 |
| C5 | **权限模型不匹配**：我们要求「文档继承源系统权限 + 先过滤后召回」；它只到**库级**，文档级要靠[人工打标签 + 工作流拼装](https://blog.fit2cloud.com/?p=019c9449-479a-71a8-909a-b78d6b6a1443) | 🟠 |
| C6 | **检索过程不可见**：它怎么切分、怎么召回、模型看到了什么，我们看不到。对要求全链路留痕的内部系统是缺口 | 🟡 |
| C7 | **能力是买来的，不是我们的**：三年后它停止演进、涨价或被收购，核心场景就悬了 | 🟡 |
| C8 | **GPLv3（社区版）/ 商业许可（专业版）**：深度定制与源码级融合受限 | 🟡 |

> **C3 是最需要正视的**：这不是"引入一个依赖"，而是"引入一个竞争对手"。避免它的唯一办法，就是**严格限制我们使用它的范围**。

---

## 4. 推荐的用法：降级为检索组件

**五条边界，写死：**

| # | 边界 | 理由 |
|---|---|---|
| **B1** | **只调用开放 API 的检索相关能力**（知识库创建、文档上传、检索） | 把它当库用 |
| **B2** | **不向最终用户暴露它的 UI** | 所有入口在我们的前端，避免双入口和双体验 |
| **B3** | **不使用它的用户体系与权限模型** | 权限**在我们这边判断**：我们按用户身份决定查哪些 `kb_id`，用服务账号调它 | 一举解决 C4 和 C5 |
| **B4** | **不用它的编排 / 工作流 / 智能体 / 企微接入** | 避免 C3 的平台竞争 |
| **B5** | **模型端点指向我们的 AI 网关** | 满足「任何服务不得绕过 AI 网关」的红线 |

**B3 是关键**：把权限判断放在我们这边，是整件事的枢纽——

- ✅ 完全避开它「文档级权限要靠人工打标签」的缺陷
- ✅ 完全避开双份用户体系同步
- ✅ 权限规则（本人 / 本部门 / 公共 / 项目组）由我们自己表达，不受它限制

代价：**MaxKB 自身的界面就不能给普通用户看**（否则绕过我们的权限）。它只对管理员开放，用于维护知识库。

```
用户 → 我们的 Agent（判断权限 → 决定 kb_id 列表）
              ↓ 服务账号 + 开放 API
         MaxKB（纯检索）
              ↓ 模型调用
         我们的 AI 网关 → 模型
```

---

## 5. 让这个决策可逆：`Retriever` 接口

这是本方案最重要的一处设计。**不要让业务代码直接依赖 MaxKB。**

```python
# app/ai/rag/base.py
class Retriever(Protocol):
    async def search(self, query: str, *, kb_ids: list[str], top_k: int) -> list[Chunk]: ...

# app/ai/rag/maxkb.py    ← 现在用这个
class MaxKBRetriever(Retriever): ...

# app/ai/rag/pgvector.py ← 将来不满意可切回自建，业务代码不改
class PgVectorRetriever(Retriever): ...
```

**判断标准**：换掉实现类不需要改任何业务代码，就说明抽象成功了。

这样我们就能：**今天用它省 3~4 人周，明天不满意随时换回自建**——决策成本被降到最低，这也是"值得用"的核心理由之一。

> 与 `13` 文档 §1.1 对 AI 网关的处理方式完全一致：**接口先定好，实现可以先外购。**

---

## 6. 什么情况下**不值得**用

以下任意一条成立，就应自建（`PgVectorRetriever`）而不是引入 MaxKB：

| 条件 | 原因 |
|---|---|
| 知识库规模小（< 500 份文档）且格式规整 | pgvector 自建只要 3~4 人周，不值得多一个系统 |
| 权限要求是**文档级 + 随源系统自动继承** | 它帮不上，还会添乱 |
| 团队 ≥ 5 人、有余力 | 自建更可控，避免 C3 |
| 需要深度定制检索策略（多路召回融合、自定义评分、混合检索权重） | 它的可控性不够 |
| 公司明确要求"只维护一套系统" | 与 C1/C2/C3 冲突 |
| 拿不到专业版的开放 API（如许可变更） | 那就只能并存，而并存是最差选项 |

## 7. 什么情况下**值得**用

| 条件 | 原因 |
|---|---|
| 团队 ≤ 3 人，工期紧 | 省 6~9 人周是实打实的 |
| 知识库格式杂（扫描件、复杂表格、多来源） | 文档解析是它最强的部分 |
| 需要快速验证场景价值 | 先跑通再优化 |
| 专业版已付费 | 边际成本接近零 |
| 短期内不需要极致检索可控性 | 用 `Retriever` 接口留好退路 |

---

## 8. 对最终方案的影响

若采纳「降级为检索组件」：

| 变化 | 说明 |
|---|---|
| ➖ **pgvector 移出 Tier 0** | 检索在 MaxKB 内完成，我们的 PG 只做关系数据 |
| ➖ 知识库管理后台不用自建 | 管理员用 MaxKB 的界面 |
| ➖ 文档解析 / 向量化流水线不用自建 | |
| ➕ `Retriever` 接口 + `MaxKBRetriever` 实现 | 约 1 人周 |
| ⚠️ MaxKB 只对管理员开放界面，不对普通用户开放 | 权限必须只由我们判断 |
| ⚠️ MaxKB 的出网权限只能到我们的 AI 网关 | |

**MVP：约 21 人周 → 约 17.5 人周（3 人约 6 周）**

**比省下的 3.5 人周更重要的是**：把风险最高、最难调优的模块（RAG 检索质量与权限过滤）移出了关键路径。

---

## 9. 集成前必须验证的 4 件事

| # | 验证项 | 不通过的后果 |
|---|---|---|
| V1 | 专业版开放 API 能否支持：**建库 / 上传文档 / 检索**三个动作 | 集成不可行，退回并存或自建 |
| V2 | 检索 API 能否返回**引用来源与片段**（我们需要展示引用） | 无法做引用溯源 |
| V3 | 模型端点能否配置为**自定义 OpenAI 兼容地址** | 无法满足统一出口红线 |
| V4 | 用服务账号调 API 时，**能否完全不依赖它的用户体系** | 无法执行 B3，双份用户体系问题回归 |

---

## 10. 最终答复

> **有必要利用，但必须限定边界。**
>
> 它是我们**已经付费的 RAG 引擎**，解决的是我们最难自己做好的部分（文档解析 + 向量化 + 检索调优），能省 6~9 人周，边际成本接近零。
>
> 但它是一个**应用层产品**，不是组件。当平台用，就会变成公司里两个 AI 平台赛跑（C3），这是最需要避免的。
>
> **正确姿势：只用它的检索 API，权限由我们判断，界面只对管理员开放，封装在 `Retriever` 接口后面。**
> 这样今天省钱、明天可换，决策成本最低。
