## 0. 关于「不用 Java」的一个提醒

很多人以为只是不写 Java 代码，但下面这些**同样跑在 JVM 上**，必须一起排除：

| 组件 | 为什么属于 JVM |
|---|---|
| Elasticsearch / OpenSearch | Java，默认 JVM 堆内存大户 |
| Apache Kafka | Scala，运行在 JVM |
| Jenkins | Java |
| Camunda / Flowable / Activiti | Java |
| Apache Tika / POI / PDFBox | Java |
| Nacos / SkyWalking / XXL-Job | Java |
| SonarQube / JMeter / Neo4j | Java |

## 1. 选型原则

1. **以团队现有能力为第一约束**——用团队熟的语言，比自己喜欢的语言重要。
2. **单一后端语言优先**——去掉 Java 后，没有理由再维持双栈；Python 单栈即可覆盖全部后端。
3. **模块化单体优先，不拆微服务**——3~6 人团队拆微服务 = 自找运维地狱。
4. **数据库能少就少**——起步 PostgreSQL 一套打通关系 + 向量 + 全文，比同时上三个中间件强。
5. **私有化部署优先**——所有组件能离线部署、许可可控。
6. **可替换性**——模型、向量库、邮件协议、连接器都能换，不让任何一家锁死。

## 4. 分层详解

### 4.1 后端：Python 单栈

去掉 Java 之后，**没有必要再维持双栈**。原来"业务在 Java、AI 在 Python"的边界，现在合并成一个 FastAPI 应用（按模块划分包边界），理由：

- 权限校验、审计、工具调用、模型调用在同一进程内完成，**省掉一整层跨服务调用**；
- Python 的异步生态（asyncpg / httpx / asyncio）足以支撑内部系统的并发量（千人级）；
- 一套依赖、一套部署、一套日志，3~6 人团队运维得动。

**模块化单体的包边界建议**

```
app/
├── api/            # 路由层（v1/...）
├── core/           # 配置、安全、依赖注入、异常
├── platform/       # 平台底座
│   ├── identity/   # 用户、组织、SSO
│   ├── authz/      # 权限（Casbin 策略）
│   ├── audit/      # 审计
│   ├── quota/      # 配额与成本
│   ├── config/     # 配置中心（Prompt、路由、开关）
│   └── notify/     # 通知中心
├── ai/
│   ├── gateway/    # LiteLLM 封装、密级路由、脱敏、缓存
│   ├── agent/      # Agent 运行时（工具调用循环）
│   ├── tools/      # 工具注册表与实现
│   └── rag/        # 检索、重排、引用
├── domain/         # 业务域
│   ├── mail/       # 邮件
│   ├── doc/        # 文档解析与生成
│   ├── calendar/   # 日程
│   ├── workflow/   # 工作流（Temporal worker）
│   └── knowledge/  # 知识库
├── connectors/     # 外部系统连接器
├── desktop_bridge/ # 桌面端指令下发与结果回传
└── workers/        # Celery / Temporal worker 入口
```

**关键库**

| 用途 | 库 |
|---|---|
| Web 框架 | FastAPI |
| ASGI 服务器 | Uvicorn（开发）/ Granian 或 Gunicorn+UvicornWorker（生产） |
| 校验 | Pydantic v2 |
| ORM | SQLAlchemy 2.0 + asyncpg |
| 迁移 | Alembic |
| 认证 | Authlib、PyJWT、python-multipart |
| 权限 | Casbin（`casbin` / `fastapi-casbin`） |
| SSE | sse-starlette |
| WebSocket | FastAPI 原生 |
| HTTP | httpx |
| 重试 | tenacity |
| 依赖注入 | FastAPI Depends（够用，不必上 dishka） |
| 日志 | structlog |
| 静态检查 | Ruff + mypy + Bandit |

### 4.2 工作流与长任务：Temporal 是本方案的关键替代

Flowable 是 BPMN 引擎，但本项目的真实需求其实是：

- 一个"批量处理 100 份合同"的任务要跑 30 分钟，中途进程重启不能丢；
- 「发邮件前等用户确认」可能要等 2 小时；
- 失败要能重试，但不能重复执行副作用（幂等）。

这些正是 **Temporal** 的强项（Durable Execution）：

| 需求 | Temporal 能力 |
|---|---|
| 断点续跑 | Workflow 状态持久化，进程崩溃后自动恢复 |
| 人工确认 | `signal` / `update` 等待外部输入，可等待任意时长 |
| 重试与幂等 | Activity 级别重试策略 + 幂等键 |
| 定时 | Cron Workflow |
| 可观测 | Web UI 直接看每个任务的状态与历史 |

代价：要接受"确定性 workflow 代码"的写法约束，且多一个 Go 服务要部署（单二进制，很轻）。

**如果团队觉得 Temporal 太重**：起步用 `APScheduler + Celery + 数据库状态机` 也能做，把"任务状态机"存表里。但一旦出现"等待人工确认数小时"的需求，就会自己造出一个劣化版 Temporal。

### 4.3 AI 层

| 项 | 选择 | 说明 |
|---|---|---|
| AI 网关 | **LiteLLM Proxy** | 统一 100+ 模型协议、路由、预算、限流、日志；自建密级路由挂在它前面 |
| 推理服务 | **vLLM**（生产）/ Ollama（开发） | OpenAI 兼容，PagedAttention 吞吐高 |
| 模型 | 外部 API + 自建覆盖敏感场景 | 见 03 文档密级路由 |
| Embedding | **BGE-M3** | 中文强、多语言、长文本 |
| Rerank | **bge-reranker-v2-m3**，用 **TEI**（Rust）部署 | 重排对 RAG 质量提升最明显 |
| OCR | RapidOCR（轻量）/ PaddleOCR（准） | 扫描件、发票 |
| 复杂版面解析 | **Docling**（首选）/ MinerU / PP-StructureV3 | 表格、多栏、公式 |
| Office 解析 | python-docx / openpyxl / python-pptx / PyMuPDF / MarkItDown | 配合 Docling 兜底 |
| RAG 编排 | **自研检索管线** + LlamaIndex 做实验 | 生产自研更可控 |
| 评测 | Ragas / DeepEval / promptfoo | 必须有回归门禁 |
| 沙箱 | Docker 受限容器 → gVisor | 代码执行必须隔离 |

> **关于 LiteLLM**：它同时是"网关"和"库"。建议**以 Proxy 模式独立部署**，这样配额、日志、密钥不随应用进程重启而丢失；应用侧只调 LiteLLM 的 OpenAI 兼容端点。

> **RAG 管线建议自研的原因**：企业内部 RAG 的难点不在"调框架"，而在**权限过滤、混合检索权重、引用溯源、增量更新**——恰好是框架最不擅长、最需要你掌控的部分。LlamaIndex 只用来快速做实验。

### 4.4 数据与存储

| 用途 | 起步 | 规模后 |
|---|---|---|
| 关系数据 | **PostgreSQL 16** | 读库 / 分区 |
| 向量检索 | **pgvector**（HNSW） | Qdrant（Rust）/ Milvus |
| 全文检索 | PG 全文（zhparser / pg_bigm / ParadeDB） | Quickwit / OpenObserve |
| 缓存 / 会话 / 限流 | **Redis 7.2** 或 **Valkey 8** | Cluster |
| 对象存储 | **MinIO** | 企业对象存储 |
| 日志 | **Loki** | Quickwit / OpenObserve |
| 消息队列 | **RabbitMQ** 或 **NATS** | —— |
| 定时 | **APScheduler** / Temporal Cron | —— |

> **反模式**：一上来就 PostgreSQL + Elasticsearch + Milvus + Kafka + Redis 五件套。3 人团队运维不动，还引入一致性问题。**起步只要 PG + Redis + MinIO 三件。**

### 4.5 可观测性

| 项 | 选择 |
|---|---|
| 埋点标准 | **OpenTelemetry**（Python SDK 成熟） |
| Trace | Tempo 或 Jaeger |
| 指标 | Prometheus + Grafana |
| 日志 | Loki + Grafana Alloy（或 Promtail） |
| **LLM 链路** | **Langfuse**（自托管）——看每次 prompt、token、成本、工具调用链 |
| 告警 | Grafana Alerting → 企微机器人 |

> Langfuse 是这个方案里性价比很高的一块：它把"AI 调用审计"和"成本分析"两件事一起解决了，能省掉不少自研。

### 4.6 基础设施与运维

| 项 | 选择 |
|---|---|
| 部署 | Docker + Compose（起步）→ **Nomad**（轻量）或 K8s |
| 网关 | Nginx（TLS / 静态 / 反代）+ FastAPI 中间件 |
| 配置 | 环境变量 + 数据库配置表 + 热更新；规模后 Consul / etcd |
| 密钥 | **HashiCorp Vault** / 云 KMS；起步用加密字段 + Docker Secret |
| 备份 | PG 主备 + WAL 归档到 MinIO；每季度恢复演练 |
| CI/CD | GitLab CI（推荐）/ Gitea Actions / Drone + Harbor |
| 压测 | Locust |
| 代码质量 | Ruff + mypy + Bandit + pre-commit |

> **关于编排**：K8s 不是 Java 技术，完全可用。但如果团队没有 K8s 经验，**Nomad** 或纯 Compose + systemd 的运维成本低得多，千人规模足够。

### 4.7 前端 / 桌面 / 移动

| 端 | 选择 | 关键点 |
|---|---|---|
| **Web** | React 18 + TS + Vite + AntD 5 | TanStack Query（服务端状态）+ Zustand（客户端状态）；**不用 Redux** |
| 流式 | **SSE**（fetch + ReadableStream） | 比 WebSocket 简单可靠；WebSocket 只用于服务端主动下发 |
| 图表 | ECharts | |
| 文档渲染 | markdown-it + PDF.js + docx-preview | 三端统一预览 |
| Monorepo | pnpm workspace + Turborepo | 共享 `ui` / `api-sdk` / `types` |
| **桌面** | **Electron 30+** + Node 20 LTS | electron-builder 打包、electron-updater 内网更新、better-sqlite3 本地索引、chokidar 文件监听 |
| 桌面安全 | `contextIsolation: true` + `nodeIntegration: false` + 白名单 IPC | |
| 本地插件协议 | **MCP 兼容** | 生态现成，其他 AI 工具也能复用 |
| **移动** | 企微自建应用 + 内置浏览器 H5 | React + Vite + AntD Mobile + 企微 JS-SDK（免登、选文件、扫一扫）+ 企微应用消息推送 |

**桌面端仍然推荐 Electron 而不是 Tauri**：本地能力重（文件 + 本地系统 + RPA + Office 解析），Node 生态现成；Tauri 要写 Rust 且依赖系统 WebView，信创适配不确定。

**不做**：React Native / Flutter / 原生 App。企微入口已经解决了分发、免登、推送三个最难的问题。

### 4.8 认证与集成

| 场景 | 方案 |
|---|---|
| Web / 桌面登录 | 企微扫码 OAuth2 → 自建 JWT（access + refresh） |
| 桌面设备绑定 | 设备指纹 + refresh token 白名单，可远程吊销 |
| 移动端 | 企微 H5 免登 |
| 备选身份源 | AD / LDAP / CAS / OIDC（Authlib 均支持） |

## 5. 备选：全 TypeScript 方案

如果团队是前端 / Node 背景为主，可以走**全 TS 单栈**：

```
NestJS + TypeScript        ← 后端
React + Vite + AntD        ← Web
Electron                   ← 桌面
Prisma / Drizzle + PostgreSQL
BullMQ（Redis）做队列；Temporal TS SDK 做工作流
```

**优点**：前后端 + 桌面同一语言，类型共享最彻底，招人容易。
**缺点**：文档解析（Docling/PaddleOCR）、RAG、评测、模型服务的生态明显弱于 Python，**这两块最终仍需一个 Python 侧服务**——等于又回到双栈，只是把 AI 侧换成 Python。

**结论**：除非团队完全没有 Python 能力，否则走 §4 的 Python 单栈更划算。

## 7. 团队与工期影响

去掉 Java 后：

| 方面 | 影响 |
|---|---|
| 团队规模 | 可少 1 人（不再需要 Java 后端 + Python 的两次对接） |
| 工期 | 平台底座阶段约省 2~3 周（少一层跨服务契约与联调） |
| 招聘 | Python 后端 + React 前端，市场供给充足 |
| 运维 | 少一个运行时（无 JVM 调优、无堆内存问题） |
| 风险 | Temporal / Docling 等非 Java 栈的团队熟悉度需要 1~2 周爬坡 |

## 8. 明确不推荐的选项

| 不推荐 | 原因 |
|---|---|
| 一上来拆微服务 | 3~6 人团队运维成本远大于收益 |
| 一上来上 K8s | Compose / Nomad 能扛住千人规模 |
| Redux / 自研组件库 | 投入产出比低，AntD 已覆盖 |
| WebSocket 做 LLM 流式 | SSE 更简单，天然支持重连与代理透传 |
| 同时上 ES + Milvus + Kafka + Redis | 起步过度设计 |
| 前端直连模型 API | key 泄露且无法配额审计——必须过网关 |
| 自研向量库 / 自研推理框架 | 纯浪费 |
| 把 LangChain/LlamaIndex 当架构 | 框架是工具，架构要自己定 |
| 用 n8n 承担核心工作流 | 许可非标准 + 复杂流程能力弱，只适合做轻量集成 |
| 用 Pandas 写在线请求路径 | 阻塞事件循环，重活一律进 worker |
