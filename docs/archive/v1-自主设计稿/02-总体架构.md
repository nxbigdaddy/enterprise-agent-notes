# 02 · 总体架构

> 版本：v1.0

---

## 1. 架构总览

```
┌──────────────────── 客户端层 ─────────────────────┐
│   Web（React）        ← MVP，唯一客户端             │
│   桌面端（Electron）  ← P1                          │
│   企微 H5             ← P1                          │
└──────────────────────┬────────────────────────────┘
                       │ HTTPS / SSE
┌──────────────────────▼────────────────────────────┐
│                   Nginx                            │
│         TLS · 静态资源 · 反向代理 · 限流             │
└──────────────────────┬────────────────────────────┘
                       │
┌──────────────────────▼────────────────────────────┐
│        FastAPI 单体应用（模块化，非微服务）           │
│                                                    │
│  ┌── platform ────────────────────────────────┐   │
│  │ identity  authz  audit  quota  config  notify│  │
│  ├── ai ──────────────────────────────────────┤   │
│  │ gateway  agent  tools  rag(Retriever)       │  │
│  ├── domain ──────────────────────────────────┤   │
│  │ chat  mail  doc  knowledge                  │  │
│  └────────────────────────────────────────────┘   │
│                                                    │
│  同镜像第二进程：scheduler（APScheduler）            │
└────────┬───────────────────────┬──────────────────┘
         │                       │
┌────────▼─────────┐   ┌─────────▼──────────────────┐
│ PostgreSQL 16    │   │  MaxKB 专业版（外部系统）     │
│ 关系数据 / 任务   │   │  知识库 + 向量检索           │
│ 审计 / 调用日志   │   │  ⚠️ 仅通过开放 API 调用      │
└──────────────────┘   │  ⚠️ 界面仅对管理员开放       │
                       └─────────┬──────────────────┘
                                 │ 模型调用
                       ┌─────────▼──────────────────┐
                       │  外部模型 API / vLLM（可选）  │
                       │  统一经 AIGateway 出入        │
                       └────────────────────────────┘
```

**部署单元 3 个**：`nginx` · `app`（含 scheduler 进程）· `postgres`。
MaxKB 是既有外部系统，不属于我们的部署单元。

---

## 2. 分层职责

| 层 | 职责 | 不该做的事 |
|---|---|---|
| 客户端 | 交互、渲染、（P1）本机能力 | 不做权限判断（服务端必须再校验） |
| Nginx | TLS、静态资源、反代、限流 | 不写业务逻辑 |
| 应用 | 业务能力、Agent 编排、权限、审计 | **不直连模型厂商**，不直连 MaxKB 以外的知识源 |
| 数据 | 关系数据、任务、审计、调用日志 | — |
| 外部 | MaxKB（检索）、模型 API | 不向其暴露我们的用户体系 |

## 3. 模块划分（包结构）

```
backend/app/
├── api/v1/            # 路由层，只做参数校验与编排
├── core/              # 配置、依赖注入、异常、日志、trace
├── platform/
│   ├── identity/      # 用户、组织（企微同步）、登录
│   ├── authz/         # 角色 / 能力 / 数据范围判定
│   ├── audit/         # 审计写入与查询
│   ├── quota/         # 配额与成本
│   ├── config/        # 配置表与热更新
│   └── notify/        # 企微机器人、站内信
├── ai/
│   ├── gateway/       # AIGateway 接口 + 实现（路由/配额/日志/降级）
│   ├── agent/         # Agent 运行时（工具调用循环）
│   ├── tools/         # 工具注册表与实现
│   └── rag/           # Retriever 接口 + MaxKBRetriever 实现
├── domain/
│   ├── chat/          # 会话与消息
│   ├── mail/          # 邮件同步与摘要
│   ├── doc/           # 文档生成（Word / Markdown）
│   └── knowledge/     # 知识库映射（kb_id ↔ 部门/范围）
├── models/            # SQLAlchemy 模型
├── schemas/           # Pydantic 模型
└── workers/           # scheduler 与任务定义
```

**跨模块规则**：`domain` 可以调 `platform` 和 `ai`；`platform` 不调 `domain`；`ai` 不调 `domain`。避免环形依赖。

## 4. 核心数据流

### 4.1 知识问答

```
用户提问
  → 鉴权 + 取用户数据范围（部门 / 密级 / 角色）
  → authz 计算「可查 kb_id 列表」
  → Retriever.search(query, kb_ids)   ← MaxKBRetriever，服务账号调用
  → 命中片段 + 引用来源
  → AIGateway.chat(scene="kb_qa", 带引用上下文)
  → SSE 流式返回答案 + 引用
  → 写 ai_call_log + audit_log（含 kb_ids、引用列表）
```

### 4.2 邮件摘要

```
scheduler 定时触发 → 拉取增量邮件（单协议）
  → 规则粗分类（发件人/主题/是否 @我）
  → 对需要处理的邮件调 AIGateway 生成摘要与待办
  → 结果落库（摘要缓存，避免重复调用）
  → 通知（站内信；P1 加企微机器人）
  → 用户在前端查看
```

### 4.3 文档生成

```
用户选择材料（本地上传 / 从会话引用）
  → 文档解析（python-docx / openpyxl / PyMuPDF）
  → 组装 Prompt → AIGateway 生成
  → 产出 Markdown → 导出 Word（python-docx）
  → 文件落本地卷，返回下载链接
  → 写审计（生成了什么、基于哪些材料）
```

## 5. 部署拓扑（Tier 0）

```
[ 8C 16G × 1 ]   应用节点
                 nginx + app(uvicorn×4) + scheduler

[ 8C 16G × 1 ]   数据库节点
                 PostgreSQL 16

[ 既有 ]         MaxKB 专业版（独立部署，我们只调 API）
[ 可选 ]         GPU 节点 / 外部模型 API
```

起步可压到**单台 8C16G**（应用 + 数据库同机），用于 PoC 与首批试点。

## 6. 目标规模与容量

| 指标 | 设计值 | 说明 |
|---|---|---|
| 用户数 | 首批 < 500，上限 2,000 | |
| 日活 | 100~400 | 按 20~40% |
| 峰值并发 | 20~50 | |
| 会话量 | ~5,000/天 | |
| 模型调用 | ~20,000 次/天 | 含 embedding（在 MaxKB 内） |
| 邮件量 | ~2,000 封/天 | 按 500 用户 |

**结论**：单应用节点（uvicorn × 4）+ 单 PG 节点足够。容量不足时的扩容顺序见 [09-部署与运维](./09-部署与运维.md) §7。

## 7. 架构红线（不可违反）

| # | 红线 | 违反后果 |
|---|---|---|
| R1 | **任何服务不得绕过 `AIGateway` 直连模型** | 配额、成本、审计全部失效 |
| R2 | **任何知识检索不得绕过 `Retriever` 接口** | 无法替换实现，被 MaxKB 锁死 |
| R3 | **权限判断必须在服务端**，客户端隐藏按钮不算 | 越权 |
| R4 | **`kb_id` 的选择必须由服务端根据用户身份决定** | 越权检索 |
| R5 | **MaxKB 界面不得对普通用户开放** | 绕过我们的权限体系 |
| R6 | **审计写入不得因业务异常而丢失** | 安全评审不通过 |

> R1 与 R2 用「接口 + 单一实现」的方式保证：换实现不改业务代码，就说明抽象成功。
