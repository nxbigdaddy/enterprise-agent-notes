# 07 · AI 能力与知识库集成

> 版本：v1.0 · 本文是**架构上最关键**的一份：两处抽象（`AIGateway` / `Retriever`）都在这里

---

## 1. 全貌

```
业务代码（domain/*）
      │  只能通过下面两个接口触达 AI
      ▼
┌─────────────────────┐        ┌──────────────────────┐
│    AIGateway        │        │     Retriever        │
│  模型统一出入口       │        │  知识检索统一接口      │
│  · 路由 / 配额 / 降级 │        │  · kb_id 由服务端决定  │
│  · 日志 / 成本 / 审计 │        │  · 引用溯源           │
└──────────┬──────────┘        └──────────┬───────────┘
           │                              │
           ▼                              ▼
   模型提供商（外部 API / vLLM）      MaxKBRetriever → MaxKB 专业版开放 API
```

**两条红线**：
- R1：业务代码不得绕过 `AIGateway` 直连模型。
- R2：业务代码不得绕过 `Retriever` 直连 MaxKB。

## 2. `AIGateway`

### 2.1 接口

```python
# app/ai/gateway/base.py
class ChatRequest(BaseModel):
    messages: list[Message]
    scene: str                 # kb_qa / mail_summary / doc_gen / default
    data_level: int = 1        # 数据密级，决定可选模型
    user_id: int
    dept_id: int | None
    trace_id: str
    temperature: float = 0.3
    stream: bool = True

class ChatResponse(BaseModel):
    content: str
    model: str
    tokens_in: int
    tokens_out: int
    cost: Decimal
    is_degraded: bool
    route_reason: str

class AIGateway(Protocol):
    async def chat(self, req: ChatRequest) -> AsyncIterator[str] | ChatResponse: ...
    async def embed(self, texts: list[str]) -> list[list[float]]: ...
```

### 2.2 实现（约 200 行，但五项职责一个都不能少）

```python
async def chat(req: ChatRequest):
    # 1. 基线检查：能力与配额
    require_capability(req.user_id, "chat.use")
    quota = check_quota(req.user_id, req.dept_id)          # 超限 → 排队 / 降级 / 阻断

    # 2. 路由：按 scene + data_level 选模型
    route = pick_route(req.scene, req.data_level)           # 见 §3
    if route is None:
        raise NoAvailableModel("无满足密级要求的模型")

    # 3. 调用（含 fallback 链）
    for model in [route.primary] + route.fallback_chain:
        try:
            resp = await call_openai_compatible(model, req)
            break
        except (Timeout, UpstreamError):
            continue
    else:
        # 4. 全失败 → 明确报错，不假装成功
        raise AllModelsFailed()

    # 5. 记账 + 审计（无论成功失败都要写）
    await write_ai_call_log(req, model, resp, route.reason)
    return resp
```

| 职责 | 说明 |
|---|---|
| **统一出口** | 业务代码里不出现任何厂商 SDK 或 API Key |
| **密级路由** | 请求带 `data_level`；机密/绝密只走内网模型 |
| **配额** | 用户 / 部门两级，超限「排队 → 降级 → 阻断」 |
| **成本台账** | 每次调用写 `ai_call_log`（模型、token、费用、耗时） |
| **Fallback 链** | 主模型失败 → 备选 → 轻量模型 → 明确报错 |
| **审计可答** | 记录 `route_reason`，能回答「为什么走了这个模型」 |

**抽象成功的判断标准**：换掉这个实现类（比如换成 LiteLLM）**不需要改任何业务代码**。

## 3. 模型路由策略

请求按以下顺序决策：

```
1. 数据密级   → 机密/绝密 ⇒ 仅内网模型；公开/内部 ⇒ 可走外部
2. 场景策略   → scene 可强制指定模型（如 mail_summary 用便宜模型）
3. 能力要求   → 长上下文 / 视觉 / 工具调用 ⇒ 过滤不支持的模型
4. 成本与配额 → 高成本模型需额度
5. 可用性     → 健康检查 + 熔断，自动切换备选
```

**MVP 建议的初始路由表**（配置在 `model_route` 表，可热改）：

| scene | 数据密级 | 主模型 | Fallback | 说明 |
|---|---|---|---|---|
| `kb_qa` | ≤ 内部 | 外部强模型 | 内网模型 | 质量优先 |
| `kb_qa` | ≥ 机密 | 内网模型 | — | 不出网 |
| `mail_summary` | ≤ 内部 | 外部中档模型 | 内网模型 | 成本优先 |
| `doc_gen` | ≤ 内部 | 外部强模型 | 内网模型 | 质量优先 |
| `default` | 任意 | 内网模型 | — | 兜底 |

> **MVP 阶段通常还没有 GPU**，此时「内网模型」可以是公司已采购的私有化实例，或临时降级为「拒绝 + 提示」。

## 4. 成本与配额

| 维度 | 默认值（可配） |
|---|---|
| 用户 | 100 万 token / 月 |
| 部门 | 部门池，按人分配 |
| 场景 | `mail_summary` 单用户 100 次/天 |
| 模型 | 高成本模型 200 次/天 |

**超限行为**：排队 → 降级到便宜模型 → 阻断并明确提示。**不要直接报错。**

**成本控制的两个要点**：
1. **摘要必须缓存**（`mail_message.summary` 字段），同一封邮件不重复调用。
2. **不缓存问答答案**——权限上下文变化会导致串数据。

## 5. `Retriever`

```python
# app/ai/rag/base.py
class Chunk(BaseModel):
    content: str
    doc_name: str
    kb_id: str
    kb_name: str
    chunk_id: str | None
    score: float | None

class Retriever(Protocol):
    async def search(self, query: str, *, kb_ids: list[str], top_k: int = 5) -> list[Chunk]: ...

# app/ai/rag/maxkb.py     ← 现在的实现
class MaxKBRetriever(Retriever): ...

# app/ai/rag/pgvector.py  ← 保留的退路，将来可实现
class PgVectorRetriever(Retriever): ...
```

**为什么必须有这层抽象**：让「今天用 MaxKB 省 3~4 人周」和「明天不满意换回自建」两个决定互不冲突。**这是整个 MaxKB 决策可逆的唯一保障。**

## 6. MaxKB 集成的五条边界（写死）

| # | 边界 | 理由 |
|---|---|---|
| **B1** | **只调用开放 API 的检索相关能力**：建库、上传文档、检索 | 把它当库用，不当平台用 |
| **B2** | **不向最终用户暴露它的 UI** | 避免双入口与双体验 |
| **B3** | **不使用它的用户体系与权限模型**；用服务账号调用 | 权限由我们判断，一举避开「文档级权限要人工打标签」与「双份组织同步」两个坑 |
| **B4** | **不用它的编排 / 工作流 / 智能体 / 企微接入** | 避免两个平台赛跑 |
| **B5** | **它的模型端点指向我们的 `AIGateway`** | 满足统一出口红线 R1 |

> **B3 是枢纽**。代价是 MaxKB 界面只能给管理员维护知识库用，不能给普通用户。

## 7. 一次知识问答的完整时序

```
用户                我们的服务端                    MaxKB             AIGateway → 模型
 │                      │                             │                     │
 │──提问───────────────▶│                             │                     │
 │                      │ 1. 鉴权 + 取用户档案         │                     │
 │                      │ 2. 计算可查 kb_ids（R4）      │                     │
 │                      │ 3. 问题改写（多轮时）         │                     │
 │                      │──search(query, kb_ids)─────▶│                     │
 │                      │◀─chunks + 引用信息───────────│                     │
 │                      │ 4. 组装 Prompt（含不可信声明）│                     │
 │                      │─────────────────────────────────────────────────▶│
 │                      │◀──────────────────── 流式答案 ───────────────────│
 │◀─SSE 流式答案 + 引用─│ 5. 写 ai_call_log + audit_log │                     │
```

**第 2 步是安全核心**：`kb_ids` 只由服务端计算，忽略客户端传参。
**第 5 步是审计核心**：记录命中的 `kb_ids` 与返回的引用列表——**检索细节我们不需要知道，但「查了什么、拿到什么」必须留痕**。

## 8. 检索策略

| 项 | MVP 做法 | 何时优化 |
|---|---|---|
| `top_k` | 5 | 引用正确率 < 85% 时调参 |
| 多轮追问 | 用「最近 2 轮 + 当前问题」改写后检索 | — |
| 多库检索 | 对 `kb_ids` 逐个或合并检索（依 MaxKB API 能力） | — |
| 重排 | **用 MaxKB 自带的重排模型**（专业版支持） | 不达标时再考虑自建 Rerank |
| 去重 | 按 `doc_name + chunk_id` 去重，避免跨库重复引用 | — |
| 分数阈值 | 低于阈值仍回答，但提示「未找到高度相关内容」 | — |
| 混合检索 | 依赖 MaxKB 的能力 | — |

## 9. 引用溯源

**每个知识类回答必须带引用卡片**，字段：

```json
{
  "kb_name": "人力资源部制度库",
  "doc_name": "员工手册 v3.2.pdf",
  "chunk_id": "xxx",
  "score": 0.87,
  "snippet": "……原文片段（≤200 字）……"
}
```

- 存到 `message.refs`（jsonb）
- 同时写入 `audit_log.detail`（脱敏后）
- 前端渲染为可折叠卡片，支持点击查看片段

**没有引用时**：回答必须显式声明「知识库中未找到相关内容」，不允许编造。

## 10. 集成前必须验证的 4 件事

**这是 MVP 第 1 周的任务，任一不通过就要改方案。**

| # | 验证项 | 不通过的后果 |
|---|---|---|
| **V1** | 开放 API 是否支持**建库 / 上传文档 / 检索**三个动作 | 集成不可行 → 退回自建 `PgVectorRetriever` |
| **V2** | 检索 API 能否返回**引用来源与片段** | 做不了引用溯源，需要额外方案 |
| **V3** | 模型端点能否配置为**自定义 OpenAI 兼容地址** | B5 无法落实，统一出口红线被破坏 |
| **V4** | 服务账号调 API 时能否**完全不依赖它的用户体系** | **B3 无法落实**，双份组织同步问题回归 |

> **V4 最关键**——它决定我们能不能把权限牢牢握在自己手里。

## 11. 降级与容错矩阵

| 故障 | 行为 |
|---|---|
| MaxKB 无响应 | 返回「知识库暂时不可用」；**不降级为纯模型回答**（会产生幻觉） |
| MaxKB 返回空 | 明确回「未找到相关内容」 |
| 主模型超时 | 走 fallback 链 |
| 全部模型失败 | 返回检索片段原文，让用户自己看；明确告知 AI 不可用 |
| 配额超限 | 排队 → 降级到便宜模型 → 阻断并提示 |
| 检索到越权内容（异常） | **阻断本次回答**，记安全事件告警（不应发生，属防御性检查） |

## 12. 迁移预案（若要切回自建）

如果 MaxKB 出现问题（API 变更、许可变更、质量不达标）：

1. 实现 `PgVectorRetriever`（约 3~4 人周：建表 + embedding 服务 + 检索）
2. 把 `kb_registry` / `kb_grant` 的授权逻辑**原样复用**（这部分本来就在我们这边）
3. 文档重新入向量库（需要一次数据迁移）
4. **业务代码零改动**——这正是 `Retriever` 抽象的价值

| 迁移触发条件 | 说明 |
|---|---|
| MaxKB 开放 API 无法满足 V1~V4 | 立即迁移 |
| 引用正确率长期 < 85% 且 MaxKB 侧无法优化 | 评估迁移 |
| 需要文档级 + 自动继承的权限模型 | 评估迁移 |
| 需要自定义检索策略（多路召回融合、自定义评分） | 评估迁移 |
| 许可变更 / 产品停止演进 | 立即迁移 |
