# 03 · 技术栈

> 版本：v1.0 · 状态：**定稿**
> 口径：Tier 0 = 现在做；Tier 1 = 有真实用户后；Tier 2 = 规模化。

---

## 1. Tier 0 定稿（就是这一套）

| 层 | 选择 |
|---|---|
| 语言 | **Python 3.12**（服务端）· **TypeScript 5**（前端） |
| Web 框架 | **FastAPI** + Uvicorn |
| 数据校验 | **Pydantic v2** |
| ORM / 迁移 | **SQLAlchemy 2.0**（async + asyncpg） + **Alembic** |
| 异步任务 | **APScheduler**（app 或独立进程）+ **PG 任务表** |
| 认证 | **Authlib + PyJWT**（企微扫码 → JWT） |
| 权限 | **自研**（角色 / 能力 / 数据范围，见 `06`） |
| AI 出口 | **`AIGateway` 接口** + httpx 实现（约 200 行） |
| 知识检索 | **`Retriever` 接口** + `MaxKBRetriever`（调 MaxKB 专业版开放 API） |
| 文档处理 | **python-docx / openpyxl / python-pptx / PyMuPDF** |
| 邮件 | **只接公司实际的那一个协议**（`msgraph-sdk` 或 `IMAPClient`） |
| 数据库 | **PostgreSQL 16**（Tier 0 **不需要 pgvector**） |
| 文件存储 | **本地磁盘卷** + `storage.py` 抽象（预留 S3 接口） |
| 前端框架 | **React 18** + **Vite** |
| 前端状态 | React 内置（useState / Context）；页面 > 15 个再引入状态库 |
| UI 组件 | **Ant Design 5** |
| 流式输出 | **SSE** |
| 日志 | **structlog → stdout**（看 `docker logs`） |
| 部署 | **Docker Compose：nginx + app + postgres** |
| 反向代理 | **Nginx** |
| 代码质量 | **Ruff + mypy + pre-commit** |

**没有的东西**：Redis · Celery · MinIO · 消息队列 · 向量数据库 · K8s · Prometheus · Grafana · Loki · OTel · Langfuse · Temporal · LiteLLM · Elasticsearch · Monorepo · ECharts。

**部署单元 3 个，语言 2 门。**

---

## 2. 为什么是这样（关键取舍）

| 决策 | 理由 | 被否方案 |
|---|---|---|
| **Python 单栈后端** | 业务 + AI 同进程，省掉一整层跨服务调用与契约维护 | Node/NestJS（AI 与文档生态弱）；Go（AI 生态弱） |
| **模块化单体** | 3 人团队；拆微服务的运维与联调成本远超收益 | 微服务 |
| **APScheduler，不用 Celery** | MVP 任务量小；少一个 Redis 与一个 worker 部署单元 | Celery + Redis |
| **自研权限三张表，不用 Casbin** | 需求只是「角色 + 能力开关 + 数据范围」，Casbin 的 policy 语法学习成本高于收益 | Casbin / OPA |
| **薄 `AIGateway`，不用 LiteLLM** | MVP 只有 1~2 个模型；接口抽象好，后期可无痛替换 | LiteLLM Proxy |
| **复用 MaxKB，不自建 RAG** | 已付费；文档解析与检索调优是它最强的部分 | pgvector 自建（保留为 `PgVectorRetriever`） |
| **本地磁盘，不用 MinIO** | 单节点，少一个组件 | MinIO / S3 |
| **Docker Compose，不用 K8s** | 单节点，< 500 用户 | K8s / Nomad |
| **React，不用服务端模板** | AI 对话需要流式渲染、Markdown、文件预览；三端要复用 | Jinja2 + htmx（仅当只有 1 名前端时的应急方案） |
| **Electron，不用 Tauri / PyQt**（P1） | 三端共用 React 代码；本机 C 生态短板用 sidecar 补 | Tauri（插件层同样弱）；PyQt（无法复用） |

## 3. Tier 0 砍掉了什么，代价是什么

| 砍掉 | 代价 | 何时加回 |
|---|---|---|
| **Redis** | 不能多节点；无分布式限流与缓存 | 应用节点 > 1 |
| **Celery** | 任务与 Web 同进程；重启丢内存态（PG 任务表可恢复） | 任务量 > 数百/天 |
| **MinIO** | 文件在本地卷，无副本，备份靠自己 | 需多节点，或文件 > 100GB |
| **Docling** | 复杂表格 / 扫描件解析质量差 | 出现扫描件或复杂版面需求 |
| **Rerank** | Top-5 命中率低一些 | 问答引用正确率 < 85% |
| **pgvector** | 无自建向量能力，检索完全依赖 MaxKB | 需要自建检索，或要做邮件/文件语义检索 |
| **Prometheus + Grafana** | 没有可视化大盘 | 有人专职做运维时 |
| **ECharts** | 没有图表 | 需要报表时 |
| **Monorepo** | 三端无法共享类型 | 第二个客户端启动时 |
| **Electron / 企微 H5** | 只有 Web 端 | MVP 三个场景验证通过后 |

> **没有一项是「以后补要返工」的**——因为都留了接口或与之无关。唯一必须现在做对的是 `AIGateway` 与 `Retriever` 两处抽象。

## 4. Tier 升级

| 规模 | 层级 | 加什么 |
|---|---|---|
| **< 500 用户，单节点** | **Tier 0** | 就是第 1 节这些 |
| 500 ~ 2,000 用户 | Tier 1 | Redis · Celery · MinIO · Rerank · 监控（Prometheus + Grafana）· Electron · 企微 H5 · 管理后台 · Monorepo · ECharts |
| > 2,000 用户 / 多节点 | Tier 2 | LiteLLM · Temporal · pgvector/Qdrant · K8s · 配置中心 · Langfuse · gVisor |

### 单个组件的触发条件（满足才加）

| 组件 | 触发条件 |
|---|---|
| Redis | 应用节点 > 1 |
| Celery | 任务量 > 数百/天，或任务需独立扩缩容 |
| MinIO | 需多节点共享文件，或文件量 > 100GB |
| Rerank | 问答引用正确率 < 85%（且 MaxKB 侧已开启重排仍不达标） |
| pgvector | 需要自建检索，或要做邮件/文件的语义检索 |
| Qdrant | 自建向量 > 500 万 chunk，或检索 p99 < 50ms |
| LiteLLM | 模型数 > 3，或需按部门发虚拟密钥 |
| Temporal | 出现「等待人工确认数小时以上」的流程，且 DB 状态机难以维护 |
| K8s | 应用节点 > 6 |
| gVisor | 需执行用户提交的任意代码 |
| Python sidecar | 出现 COM / Office 自动化、Windows UIA、或厂商硬件 DLL 需求 |

## 5. 明确不推荐

| 不推荐 | 原因 |
|---|---|
| 任何 Java / JVM 技术 | 硬性约束（注意：**Elasticsearch / Kafka / Jenkins / Camunda 都属于 JVM**） |
| 微服务拆分 | 团队规模不匹配 |
| 前端直连模型 API | key 泄露且无法配额审计 |
| 业务代码直接 import 厂商 SDK | 无法替换，绕过网关 |
| 业务代码直接调 MaxKB | 绕过 `Retriever`，被锁死且无法替换 |
| WebSocket 做 LLM 流式 | SSE 更简单，天然支持重连与代理透传 |
| 用 Pandas 写在线请求路径 | 阻塞事件循环，重活一律进任务 |
| 把 LangChain / LlamaIndex 当架构 | 框架是工具，架构自己定 |
| 同时上 ES + Milvus + Kafka | 起步过度设计 |
| 自研向量库 / 自研推理框架 | 纯浪费 |
