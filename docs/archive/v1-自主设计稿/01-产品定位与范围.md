# 01 · 产品定位与范围

> 版本：v1.0

---

## 1. 定位

**公司内部统一的 AI 办公入口。**

| 关键词 | 含义 |
|---|---|
| **统一入口** | 员工不再需要在十几个系统和无数个 AI 网页之间切换 |
| **能干活** | 不止回答问题，还能读邮件、查知识、生成 Word/PPT 文件 |
| **可治理** | 因为它能碰公司数据，所以权限、审计、成本与业务能力同等重要 |

### 我们不是什么

- ❌ 一个套壳的 ChatGPT 网页
- ❌ 给每个部门各买一套 SaaS 的替代品
- ❌ 一个独立的「知识问答产品」——知识问答只是三个场景之一（且检索层复用 MaxKB）
- ❌ 把人替换掉的自动化流水线

---

## 2. 用户角色

| 角色 | 谁 | 核心诉求 |
|---|---|---|
| **员工**（默认） | 全员 | 上手即用、答案可信、能直接出文件 |
| **部门管理员** | 部门骨干 | 能管本部门的知识库、模板、成员额度 |
| **平台管理员** | 信息中心 | 可控、可查、成本可核算 |
| **安全 / 合规** | 风控、内审 | 数据不越界、全程留痕、可追责 |

> **设计含义**：同一个人在不同场景下可能是多个角色，权限模型必须支持角色**叠加**，而不是一人一角色。

---

## 3. 场景与优先级

### 3.1 MVP（P0）—— 只做这三个

| 场景 | 用户价值 | 关键实现 | 依赖 |
|---|---|---|---|
| **知识问答** | 问公司制度/流程，答案带出处 | 调 MaxKB 检索 → 组装 → 引用溯源 | MaxKB 开放 API |
| **邮件摘要** | 长邮件一句话说清，抽出待办 | 邮件同步 + 模型摘要 | **邮件系统 API 权限** |
| **文档生成** | 周报/汇报从零散材料一键成稿 | 材料汇聚 + 生成 + 导出 Word | 无外部依赖 |

**选择标准**：价值高、依赖少、能在 6 周内跑通闭环。

### 3.2 P1 —— 验证通过后做

邮件发送（人工确认）· 桌面端 · 企微 H5 · 管理后台 · 待办中心 · 日程会议 · 模板中心 · 工作流与定时 · 完整监控

### 3.3 P2 及以后 —— 长期路线

连接器（OA/ERP/CRM/HR）· OCR 与复杂文档解析 · 会议转写 · 评测体系 · 技能市场 · 数据问答

完整能力清单见 [05-功能规格](./05-功能规格.md) 附录。

## 4. 设计原则

1. **交付可用的东西**——用户要的是报告、邮件草稿、表格，不是一个聊天回答。
2. **可信优先于聪明**——知识类回答必须带来源；无来源时必须明说「不确定」，不允许编造。
3. **人机协同，不是全自动**——从「AI 做 → 人确认」起步，逐步放开到「AI 做 → 事后审计」。
4. **默认最小权限**——能力与数据都需显式开通，默认拒绝。
5. **服务端是唯一事实源**——客户端只做展示与本机能力代理。
6. **先跑通闭环，再谈智能**——一个能稳定完成周报的窄场景，价值高于十个演示级 Demo。

---

## 5. 范围边界（明确不做）

| 不做 | 原因 |
|---|---|
| 自主对外发信（无人工确认） | 风险远大于收益 |
| 替代正式审批流 | 合规要求签批留痕；我们只做「辅助填单」 |
| 原生移动 App | 企微入口已解决分发、免登、推送 |
| 自研基础大模型 | 成本与收益不成比例 |
| 自研 RAG 检索引擎（MVP 阶段） | 已付费的 MaxKB 够用；用 `Retriever` 接口留退路 |
| RPA / 浏览器自动化 | 老系统适配是无底洞 |
| 多 Agent 协作 | 演示价值 > 实用价值 |
| 面向外部客户 | 内部系统定位不同，单独立项 |

---

## 6. 成功指标

| 维度 | 指标 | 目标（MVP 后 1 个月） |
|---|---|---|
| 采用度 | 周活跃 / 覆盖人数 | ≥ 40%（首批试点范围内） |
| 深度 | 人均周会话数 | ≥ 5 |
| 价值 | 自评每周节省时间 | ≥ 2 小时 |
| 质量 | 知识问答**引用正确率** | ≥ 85% |
| 质量 | 幻觉率（无依据却给肯定答案） | ≤ 5% |
| 安全 | 越权访问事件 | **0** |
| 安全 | 敏感信息外发事件 | **0** |
| 稳定 | 核心接口可用性 | ≥ 99% |
| 成本 | 单活跃用户月成本 | 设定硬上限并监控 |

> **采用率是最大风险**。功能做得再多，没人用就是零。因此首批必须选**真实痛点部门**，并配驻场支持。

## 7. 关键假设与待验证点

| # | 假设 | 验证方式 | 不成立的后果 |
|---|---|---|---|
| A1 | 员工最大痛点是「信息分散 + 重复写作」 | 访谈首批试点部门 | 场景选错，全盘返工 |
| A2 | 邮件系统可开放 API / IMAP | **第 1 周验证** | MVP 少一个场景，需替换 |
| A3 | 企微自建应用可创建并回调 | **第 1 周验证** | 登录链路阻塞 |
| A4 | MaxKB 专业版开放 API 支持建库/上传/检索，且可脱离其用户体系 | **第 1 周验证** | 集成不可行，退回自建 |
| A5 | 知识库有可用内容且有人负责 | 确认内容责任人 | 知识问答场景失效 |

> A1~A5 的验证在第 1 周完成，详见 [10-实施计划](./10-实施计划.md) §4。
