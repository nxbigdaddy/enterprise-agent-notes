# 11 · 架构决策记录（ADR）

> 版本：v1.0
> 每条 ADR 记录：**决策 / 背景 / 理由 / 被否方案 / 变更触发条件**。
> 变更流程：先满足触发条件，再改文档，并在本表末尾登记。

---

## ADR-01 · 不使用任何 Java / JVM 技术

| | |
|---|---|
| **决策** | 技术栈中不引入任何 Java / JVM 组件 |
| **背景** | 需求方硬性约束 |
| **注意** | 很多人只想到 Spring，但这些**同样跑在 JVM 上**，必须一并排除：Elasticsearch / OpenSearch（Java）、Apache Kafka（Scala）、Jenkins（Java）、Camunda / Flowable（Java）、Apache Tika / POI / PDFBox（Java）、Nacos / SkyWalking / XXL-Job（Java） |
| **影响** | 后端语言限定为 Python（AI 生态最好）；日志检索改用 Loki；全文检索改用 PG 原生；工作流用 DB 状态机；CI 用 GitLab CI |

---

## ADR-02 · Python 单栈后端（而非 Java + Python 双栈）

| | |
|---|---|
| **决策** | 后端全部用 Python 3.12 + FastAPI |
| **背景** | 去掉 Java 后，原本「业务在 Java、AI 在 Python」的分界失去意义 |
| **理由** | 权限校验、审计、工具调用、模型调用在同一进程内完成，省掉一整层跨服务调用与契约维护；一套依赖、一套部署、一套日志 |
| **被否** | Java + Python 双栈（约束不允许）；Node/NestJS（AI 与文档解析生态弱）；Go（AI 生态弱） |
| **触发条件** | 出现 Python 无法满足的性能瓶颈（如单接口 > 1000 QPS）时，再评估把特定模块用 Go 重写 |

## ADR-03 · 模块化单体（而非微服务）

| | |
|---|---|
| **决策** | 单个 FastAPI 应用，按 `platform / ai / domain` 划分包边界 |
| **理由** | 3 人团队；微服务的部署、联调、可观测成本远超收益；< 500 用户的负载单进程足够 |
| **被否** | 微服务拆分；Serverless |
| **触发条件** | 团队 > 10 人，或某模块需要独立扩缩容（如文档解析）时，再考虑拆分 |

## ADR-04 · Tier 0 只有 3 个部署单元

| | |
|---|---|
| **决策** | `nginx` + `app`（含 scheduler）+ `postgres` |
| **背景** | 早期方案有 6+ 个部署单元，被反馈「过于复杂」 |
| **理由** | 最小可验证；单节点即可支撑 MVP；每多一个组件就多一份运维与故障面 |
| **被否** | Redis · Celery · MinIO · 消息队列 · 向量数据库 · K8s · Prometheus · Grafana · Loki |
| **触发条件** | 见 `03-技术栈.md` §4 的逐组件触发条件 |

## ADR-05 · PostgreSQL 而非 MySQL

| | |
|---|---|
| **决策** | PostgreSQL 16 |
| **理由** | ① 扩展生态（pgvector / pg_trgm / 分区 / FDW）② JSONB + GIN 索引能力更强 ③ DDL 事务性、约束能力更强 ④ 复杂查询与并行查询更强 |
| **被否** | MySQL（国内 DBA 更多、中文全文检索开箱可用——**这两点是 MySQL 的真实优势，但本项目中不构成决定性因素**） |
| **备注** | Tier 0 阶段 **不需要 pgvector**（检索复用 MaxKB）；pgvector 是未来自建检索时才需要 |
| **⚠️ 实现注意** | **不要用 `to_tsvector('simple', content)` 做中文全文检索**——PG 默认解析器会把整段无空格中文当成一个 token，索引等于没用。中文兜底用 `pg_trgm`；真要分词检索再装 `zhparser` / `pg_bigm` |
| **触发条件** | 几乎没有。除非公司强制要求 MySQL 生态 |

## ADR-06 · 复用 MaxKB 专业版作为检索组件

| | |
|---|---|
| **决策** | 知识检索复用已有 MaxKB 专业版，**但只作为检索组件，不作为并列平台** |
| **背景** | 公司已有 MaxKB 专业版（开放 API / RBAC / SSO 均可用） |
| **理由** | ① 已付费，边际成本接近零 ② 它解决的正是我们最难做好的部分：文档解析、切分、向量化、检索调优 ③ 省 6~9 人周 |
| **被否** | 完全自建 RAG（多花 3~4 人周，且第一版质量大概率不如成熟产品）；把 MaxKB 当主平台（会造成**两个 AI 平台在公司内赛跑**——它的演进方向与我们高度重叠） |
| **代价** | 多一个外部依赖；检索过程不可见（但「查了什么、拿到什么」可留痕） |
| **触发条件** | 见 `07-AI能力与知识库集成.md` §12 的迁移条件 |

## ADR-07 · 权限判断在我们这边（MaxKB 五条边界）

| | |
|---|---|
| **决策** | `kb_id` 列表由**我们的服务端**根据用户身份计算；MaxKB 只接受服务账号调用，其界面**不对普通用户开放** |
| **理由（关键）** | 一举避开两个坑：① MaxKB 的文档级权限要靠**人工打标签 + 工作流拼装**，运维负担重 ② 用它自己的用户体系会导致**双份组织架构同步** |
| **代价** | MaxKB 自身的权限能力被放弃；界面只能给管理员维护知识库用 |
| **五条边界** | B1 只用检索 API · B2 不暴露 UI · B3 不用其用户体系 · B4 不用其编排/工作流 · B5 模型端点指向我们的 AIGateway |
| **触发条件** | 若业务需要 MaxKB 的智能体/工作流能力，需重新评估（届时会冲突） |

## ADR-08 · 内部 `AIGateway` 接口，而非引入 LiteLLM

| | |
|---|---|
| **决策** | 自研约 200 行的 `AIGateway`，实现统一出口、密级路由、配额、成本台账、fallback、审计 |
| **理由** | MVP 只有 1~2 个模型；引入 LiteLLM 是为将来付费。但**接口必须先抽象好**，后期可无痛替换 |
| **被否** | LiteLLM Proxy（Tier 1 备选）；业务代码直连模型（红线 R1） |
| **判断标准** | 换掉实现类不需要改任何业务代码 |
| **触发条件** | 模型数 > 3，或需按部门发放虚拟密钥 → 切 LiteLLM |

## ADR-09 · APScheduler + PG 任务表，而非 Celery + Redis

| | |
|---|---|
| **决策** | 任务落 `job` 表，APScheduler 负责触发；不做独立 worker |
| **理由** | MVP 任务量小（邮件同步、摘要、文档生成）；省掉 Redis 与一个部署单元 |
| **被否** | Celery + Redis；Temporal（引入 Go 服务 + 确定性编程约束） |
| **风险** | 任务与 Web 同进程，重启丢内存态 → 用 `job` 表 + `idempotency_key` 缓解 |
| **触发条件** | 任务量 > 数百/天，或需独立扩缩容 → Celery；出现「等待人工确认数小时以上」的流程 → Temporal |

## ADR-10 · 本地磁盘卷，而非 MinIO

| | |
|---|---|
| **决策** | 文件存本地卷，通过 `storage.py` 抽象（预留 S3 接口） |
| **理由** | 单节点；少一个组件 |
| **风险** | **无副本，备份是唯一保障**——这是 Tier 0 最薄弱的一环 |
| **触发条件** | 需多节点共享文件，或文件量 > 100GB → MinIO |

| | |

| **触发条件** | — |

## ADR-12 · 桌面端用 Electron（P1）

| | |
|---|---|
| **决策** | Electron 30+ + Node 20 LTS，复用 Web 端 React 代码 |
| **理由** | 本地能力重（文件 + 本地系统 + Office 解析），Node 生态现成；三端共用 UI 与类型 |
| **被否** | **Tauri**（在「调 C 生态」上和 Electron 一样弱，换外壳解决不了核心问题，只是把 UI 层换成 Rust）；**Python GUI / PyQt**（无法与 Web 端复用任何代码，且 AI 对话的流式渲染、Markdown、图表在 PyQt 中是逆风局） |
| **触发条件** | 包体/内存成为硬指标 → 评估 Tauri（插件层无需改动，只换外壳） |

## ADR-13 · 企业微信为组织事实源

| | |
|---|---|
| **决策** | 部门树与人员以企微通讯录为准；Web/桌面扫码登录，H5 免登 |
| **理由** | 移动端入口就是企微，避免双源冲突；企微同时解决分发、免登、推送三个最难的问题 |
| **被否** | AD / LDAP 为主（若公司已以 AD 为准，需重新评估——见待确认 Q1） |
| **触发条件** | 公司组织事实源明确为 AD 且与企微不一致时 |

## ADR-14 · SSE 而非 WebSocket 做流式

| | |
|---|---|
| **决策** | 模型输出用 SSE（`text/event-stream`） |
| **理由** | 更简单；天然支持断线重连与代理透传；单向推送语义匹配 |
| **被否** | WebSocket 做流式（复杂且无必要） |
| **触发条件** | P1 桌面端需要服务端**主动**下发（工具指令、通知）时，再引入 WebSocket——两者可并存，用途不同 |

## ADR-15 · 自研权限表，而非引入 Casbin

| | |
|---|---|
| **决策** | 自研 `role` / `capability` / `user_capability` / `data_scope_rule` 四类表 |
| **理由** | 需求只是「角色 + 能力开关 + 数据范围」；Casbin 的 policy 语法学习成本高于收益 |
| **被否** | Casbin / OPA |
| **触发条件** | 策略复杂到需要表达资源级条件（如「仅可编辑自己创建的、状态为 draft 的文档」）时再评估 |

## ADR-16 · 审计自建表，而非引入 Langfuse

| | |
|---|---|
| **决策** | 用 `audit_log` + `ai_call_log` 两张表承载审计与 LLM 观测 |
| **理由** | 与自建审计中心功能重复；少一个服务 |
| **被否** | Langfuse（自托管） |
| **触发条件** | 需要 prompt A/B 对比与自动化评测流水线 → 引入 Langfuse |

## ADR-17 · 桌面端 Python sidecar 按需引入（P1/P2）

| | |
|---|---|
| **决策** | 默认纯 Node；**只有**出现 COM / Office 自动化、Windows UI Automation、厂商硬件 DLL 需求时才挂 Python sidecar |
| **理由** | sidecar 带来三重成本：体积（+40MB 起，带 OCR 可达 300MB+）、冷启动（1~3s）、杀软误报（需代码签名） |
| **实现建议** | 本地插件协议做成 **MCP 兼容 + stdio 传输**，则 Python sidecar 天然是本地 MCP Server，无需另造协议 |
| **触发条件** | 出现上述任一需求 |
