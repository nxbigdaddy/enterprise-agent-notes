## 1. 范围收敛后的账

原始需求里有「桌面端和 Web 端互通、移动端走企微浏览器」的**三端**诉求。经确认：

| 诉求 | 决定 | 影响 |
|---|---|---|
| 桌面端 | ✅ **已有**（PySide6，32,162 行） | 无需工作 |
| Web 端 | ❌ **不做**（原架构即 Python 桌面端，Web 无必要） | 我们原 MVP 的 3.5 人周前端工作**归零** |
| 移动端 / 企微 H5 | ❌ **不做**（原系统未规划，维持） | 省 2~3 人周 |

**因此我们原 MVP（17.5 人周）的构成全部失效**：
- 邮件摘要 2.5 → **已完成**
- 文档生成 2.0 → **已完成**
- Web 前端 3.5 → **不做**
- 后端骨架+登录+权限 2.0 → **已完成**
- AIGateway 1.0 → **已完成且远超**
- MaxKB 集成 1.0 → **80% 完成**
- 审计+通知 1.0 → **已完成**
- 部署 0.5 → **已完成且已上线**
- 测试返工 4.0 → 已有 289 pytest + 79 vitest 兜底

**剩余：一个 SQLServer 连接器。**

## 2. 唯一的代码缺口：SQLServer 只读连接器

### 2.1 现状核实

在 `platform_api/connectors.py` 中检索 `sqlserver|mssql|pymssql|pyodbc` —— **零匹配**。

现有企业连接器只支持两类：
1. **HTTP GET 连接器**（`http` / `https`）
2. **MySQL 只读连接器**（`mysql+pymysql`）

且 MySQL 是**硬编码**的：

| 位置 | 代码 | 问题 |
|---|---|---|
| L521 | `{"mysql+pymysql"} if connector_type == "database" else {"http","https"}` | 驱动白名单只放 MySQL |
| L568 | `credential_url.drivername != "mysql+pymysql"` | 凭据校验只认 MySQL |
| **L706** | `SELECT /*+ MAX_EXECUTION_TIME({timeout_ms}) */ ...` | 🔴 **这是 MySQL 专有优化器提示，SQLServer 不支持** |
| L787 | `_safe_identifier` | 需确认标识符引用规则（MySQL 反引号 vs SQLServer `[]`） |
| L669 | `_execute_database` | 行数限制语法（`LIMIT n` vs `TOP n`） |

> **关键**：L706 说明耦合不只在驱动层，而在 **SQL 构造层**。所以这不是「加个依赖」就行，需要按方言分支。

### 2.2 工作量估算

| 项 | 内容 | 人周 |
|---|---|---|
| 依赖 | 引入 `pymssql`（纯 Python 友好）或 `pyodbc` | 0.1 |
| 驱动白名单 | 放开 `mssql+pymssql`（L521） | 0.1 |
| 凭据校验 | 同步放开（L568） | 0.1 |
| **超时机制** | 按方言分支：SQLServer 用连接级 `command timeout` 或 `SET LOCK_TIMEOUT`，替换 `MAX_EXECUTION_TIME` 提示 | 0.4 |
| 标识符引用 | 按方言加引号（`[]` vs 反引号） | 0.2 |
| 行数限制 | `TOP n` vs `LIMIT n` | 0.2 |
| 管理端 UI | `ConnectorsPage` 连接器类型下拉 + 凭据表单增加 SQLServer 选项 | 0.2 |
| 测试 | 参照现有连接器测试补 SQLServer 用例（可用 SQLite/mock 覆盖方言分支） | 0.3 |
| **合计** | | **约 1.5** |

**底线：1 人周可交付。**

### 2.3 设计约束（不能破的既有红线）

新增连接器必须维持现有安全模型（来自 ADR-008 与 `implementation-status.md` FR-SYS-001）：

1. **只生成 `SELECT`**，且仅限**已批准的视图、字段、等值筛选**和**行数上限**
2. 必须返回**来源 / 条件 / 口径 / 数据时间**
3. **禁止写入**（数据库连接器写操作已被明确禁止）
4. 服务端连接，**客户端不直连生产库**
5. 复用现有一次性授权令牌与审计链路，不新增旁路

> 换句话说：**只加方言适配，不加新能力。**

## 4. 你这次的回答澄清的两件事

### 4.1 Q3 揭示了一个真实缺口

> 「公司内部其他系统数据库多种多样，mysql、sqlserver 都有；其他系统连接有的可以直接连库，有的可以用 API」

对照现状：
- ✅ HTTP/API 连接器 —— **已有**
- ✅ MySQL 直连 —— **已有**
- ❌ **SQLServer 直连 —— 没有** ← 本次唯一新增开发

### 4.2 MySQL 不是硬约束

> 「mysql 不是必须的。之前使用了而已。」

含义：**数据库选型可以按工程最优决定，不必迁就公司标准**。但鉴于：
- 生产/测试**已部署在 MySQL 并到 migration head**
- 32 个 Alembic 迁移已跑通
- 换库 = 重写迁移 + 全量重测

**建议维持 MySQL。** 「不是必须」意味着**将来新模块可以自由选型**，而不意味着现在应该换。这条应记入 ADR。

| ADR（原 `11-架构决策记录.md`） | 原结论 | 修订为 | 理由 |

| ADR-05 PostgreSQL | PostgreSQL 16 | **MySQL 8.0**（维持现状） | 已部署上线；「非必须」不等于「应更换」 |
| ADR-12 Electron | Electron 而非 Python GUI | **PySide6**（维持现状） | 已有 32,162 行已验证代码；重写是净损失 |
| ADR-11 React 18 + AntD | React 18 | **React 19**（维持现状） | 管理后台已是 React 19 + Vite + TS + vitest |
| DR-14 MVP 范围 | 3 场景 + Web 端 | **不需新建，仅补 SQLServer 连接器** | 范围确认 |
| ADR-06/07 MaxKB | 复用为检索组件 | **维持** | 与其 ADR-009 一致；但**降级期望**：只做应用级问答，建库/上传需系统 API |

### 5.1 关于我此前 ADR-12 判断的说明

我在 `11` 号文档写过「用 PyQt 做 AI 办公客户端，是用最不擅长的工具打最需要体验的仗」。

**那个判断的前提是「从零开始、且需三端复用 React」。** 前提不成立，结论就要反过来——而且 AI-DeskTop 自己的 ADR-001 已给出同样结论（PySide6，替代方案 Tauri/React + Python sidecar）。

## 8. 结论

> **AI-DeskTop 不是「可复用的基础」，它就是产品。**
>
> 范围收敛（不做 Web、不做移动端）之后，我们要做的事从「17.5 人周的新系统」变成「**1.5 人周补一个 SQLServer 连接器 + 若干现场联调**」。

> 这轮评估最大的价值不是「省了多少代码」，而是**避免了重复造一个更差的轮子**。
